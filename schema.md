# Wiki Schema

This is the canonical reference for how any LLM should interact with this wiki.
Read this file before any wiki operation (ingest, query, lint, staleness check).

## Purpose

This wiki is a persistent, LLM-maintained knowledge base. Unlike RAG (which re-derives
answers from raw documents on every query), the wiki **compiles knowledge once and keeps
it current**. Cross-references, contradictions, and synthesis are maintained incrementally
as new sources are added. The LLM writes and maintains all wiki content; the human curates
sources, directs analysis, and asks questions.

This wiki is separate from Claude's auto-memory system. Auto-memory is for ephemeral
session context (active branches, quick feedback). The wiki is for durable, structured
knowledge that compounds over time.

## Directory Layout

```
~/wiki/
  schema.md              # this file — shared across all vaults
  bin/
    check-stale          # staleness detection script (see Staleness Check below)
  {vault}/               # one directory per vault (e.g. azimuth/, personal/)
    _meta/
      index.md           # tag-grouped page catalog (regenerated by lint)
      log.md             # append-only activity log
      tags.md            # controlled tag vocabulary
    _sources/
      {slug}.md          # immutable captured source documents
    {slug}.md            # wiki pages (LLM-generated and maintained)
```

- File names use `kebab-case` slugs
- `_meta/` and `_sources/` use underscore prefix to sort first and signal "not a wiki page"
- Wiki pages are flat in the vault root — no subdirectories

## Page Format

Every wiki page has YAML frontmatter followed by markdown content.

```yaml
---
title: Page Title
tags: [tag-a, tag-b]
sources:
  - path: web-app/src/charts/timeseries/    # repo reference
    last_read: 2026-04-12
  - file: some-article-slug                  # captured source in _sources/
created: 2026-04-12
updated: 2026-04-12
last_accessed: 2026-04-12
---

Content here. Use [[wikilinks]] to link to other pages.
```

Required fields: `title`, `tags`, `created`, `updated`, `last_accessed`
Optional fields: `sources` (omit if the page is purely synthesized from other wiki pages)

**`last_accessed` semantics:** Set to today's date whenever the LLM reads the page
during a query, ingest, lint, or staleness operation. This is distinct from
`updated` (which tracks content changes) and `last_read` under `sources` (which
tracks when the LLM last read the underlying source path). `last_accessed`
records LLM attention on the wiki page itself and is used to identify pages that
have gone cold.

**Content guidelines:**
- Lead with a concise summary (2-3 sentences)
- Use headers to structure longer pages
- Link liberally to other wiki pages with `[[slug]]` wikilinks
- When a page references specific claims, cite the source with `[[slug]]` or note the repo path
- Update the `updated` date whenever the page content changes

## Source Types

### Captured Sources (`_sources/{slug}.md`)

External content that doesn't live in the repo — articles, Slack threads, meeting notes,
papers. These are immutable snapshots. The LLM reads from them but never modifies them.

```yaml
---
title: "Article or Document Title"
type: article              # article | doc | slack-thread | meeting-notes | paper
url: https://...           # original URL if external; omit for internal content
ingested: 2026-04-12
---

Content of the source document.
```

### Repo References

Paths within the project repo that the LLM reads directly from the worktree at ingest
time. Nothing is copied — the wiki page records the path and `last_read` date in its
`sources` frontmatter. Any active worktree can be used for reading (they all share the
same repo content modulo branch differences).

```yaml
sources:
  - path: web-app/src/charts/timeseries/
    last_read: 2026-04-12
```

## Operations

### Ingest (Captured Source)

1. User drops a file in `_sources/` or pastes content for the LLM to save there
2. Read the source document
3. Discuss key takeaways with the user
4. Write a summary wiki page (or update an existing one) with proper frontmatter
5. Update other wiki pages where the new source adds, changes, or contradicts information
6. Append an entry to `_meta/log.md`

### Ingest (Repo Path)

1. User says "ingest `path/to/dir/`" (or a specific file)
2. Read files at that path in the current worktree
3. Discuss findings with the user
4. Write or update wiki pages with `path:` and `last_read:` in the sources frontmatter
5. Update other wiki pages where the new information is relevant
6. Append an entry to `_meta/log.md`

**When to create a new page vs update existing:** If the ingested content maps to an
existing wiki page's topic, update that page. If it covers a new topic, create a new page.
When in doubt, ask the user.

### Query

1. Read `_meta/index.md` to find relevant pages
2. Read those pages and follow `[[wikilinks]]` to gather related context
3. Bump `last_accessed: <today>` in the frontmatter of every wiki page read
4. Synthesize an answer with `[[wikilink]]` citations to wiki pages
5. If the answer produces a valuable synthesis (comparison, analysis, connection), offer
   to file it as a new wiki page so the work compounds

### Access Tracking

Whenever the LLM reads a wiki page (during query, ingest, lint, or staleness check),
update that page's `last_accessed` field to today's date before moving on. Do not
update `updated` — that field is reserved for content changes. Batch the writes when
multiple pages are touched in one operation.

### Lint

1. Regenerate `_meta/index.md` from all wiki page frontmatter (grouped by tag)
2. Check for:
   - Contradictions between pages
   - Stale repo references (`last_read` older than latest changes to that path via `git log`)
   - Orphan pages (no inbound wikilinks from other pages)
   - Missing pages (wikilinked but don't exist)
   - Unregistered tags (used in frontmatter but not in `_meta/tags.md`)
   - Important concepts mentioned but lacking their own page
3. Truncate `_meta/log.md` to last 50 entries (archive older entries to `_meta/log-archive.md`)
4. Report findings — fix mechanical issues, flag judgment calls for the user

### Staleness Check

After modifying repo files, run `~/wiki/bin/check-stale` to find wiki pages whose
source path references overlap with changed files.

```bash
# Pipe changed files
git diff --name-only | ~/wiki/bin/check-stale

# Or pass as args
~/wiki/bin/check-stale path/to/changed-file.ts

# Or let it default to git diff HEAD~1
~/wiki/bin/check-stale
```

If the script reports affected pages and the changes are substantive (not just formatting
or trivial edits), read the affected wiki pages and update them to reflect the new state
of the source code.

## Tag Vocabulary

Tags are defined in `_meta/tags.md` with descriptions. When tagging a page:
- Use existing tags from `_meta/tags.md` when they fit
- Propose a new tag if no existing tag covers the concept — add it to `_meta/tags.md`
  with a one-line description
- Pages should have 1-4 tags; prefer specificity over breadth

## Adding a New Vault

To create a new vault (e.g. `~/wiki/personal/`):

1. `mkdir -p ~/wiki/{vault}/_meta ~/wiki/{vault}/_sources`
2. Create `_meta/tags.md` with domain-appropriate tags
3. Create empty `_meta/index.md` and `_meta/log.md` using the same format
4. This schema applies to all vaults — no vault-specific overrides needed unless
   the domain requires different conventions (in which case, add
   `{vault}/_meta/schema-overrides.md`)
